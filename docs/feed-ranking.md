# 피드 랭킹 — 가중치 정규화 방안

대상: `com.knowra.post.service.FeedService#computeScore`
작성 근거: 2026-09-23 로컬 PostgreSQL 시드(게시글 112건, 사용자 49명) 실측

---

## 1. 진단 — 가중치가 비중이 아니다

현재 총점은 다섯 축의 가중합이다.

```java
totalScore = interestMatchScore * 0.15   // 관심사
           + relationScore      * 0.25   // 관계
           + qualityScore       * 0.25   // 품질
           + freshnessScore     * 0.20   // 신선도
           + exploreScore       * 0.15;  // 탐험
```

가중치가 "비중"이 되려면 곱해지는 값들이 **같은 자로 재어져야** 한다. 지금은 아니다.
각 축의 원점수는 정의상 범위가 전혀 다르다.

| 축 | 원점수 정의 | 실측 범위 |
|---|---|---|
| 관심사 | 태그 점수의 합 | 0 ~ 12 |
| 관계 | 15/20 플래그 + 친밀도 | 0 ~ 50 |
| 품질 | `like×2 + cmt×4 + view×0.2` (누적 총량) | 0 ~ 3,598 |
| 신선도 | `100 / √(경과시간+2)` | 1.6 ~ 57.7 |
| 탐험 | `(1-친숙도) × 신규성 × 20` | 0 ~ 20 |

품질만 세 자릿수다. 가중치를 곱한 뒤 실제로 순위를 흔드는 양(표준편차)을 재면 이렇게 된다.

| 축 | 명목 가중치 | **실제 순위 기여도** |
|---|---|---|
| 관심사 | 15% | 0.2% |
| 관계 | 25% | 1.4% |
| 품질 | 25% | **97.8%** |
| 신선도 | 20% | 0.0% |
| 탐험 | 15% | 0.6% |

가장 신호가 풍부한 계정(태그 7개, 팔로잉 13명, 커뮤니티 6개)으로 개인화 순서와
순수 인기순을 비교한 결과다.

```
스피어만 상관       0.9992
순위가 완전히 같음   112건 중 59건
평균 순위 이동      0.77 칸
최대 순위 이동      4 칸
```

**개인화 피드는 인기순이다.** 축이 다섯 개인 게 아니라 하나다.

원인은 두 가지가 겹쳐 있다.

- **척도 불일치** — 위 표 그대로다.
- **품질이 누적 총량** — 6개월 된 글도 그동안 쌓은 조회수를 영구히 유지한다.
  신선도는 더해지는 항이라 이 격차를 되돌리지 못한다.

## 2. 정규화만으로는 안 되는 두 번째 결함

**관심사와 탐험이 같은 신호를 부호만 바꿔 쓰고 있다.**

```java
double novelty = tagSns.stream()
        .mapToDouble(t -> userTagScores.getOrDefault(t, 0.0) == 0.0 ? 1.0 : 0.0)
        .average().orElse(0.0);
```

`novelty` 는 "내 태그와 안 맞을수록 1" 이고, `interestMatchScore` 는 "맞을수록 크다" 이다.
정의상 서로의 뒤집힌 값이다. 실측 상관은 **-0.9226**.

즉 W1(0.15)으로 밀어올린 글을 W6(0.15)이 거의 같은 크기로 도로 끌어내린다.
태그 기반 개인화의 순효과는 **0에 수렴한다.** 척도를 맞춰도 이 상쇄는 그대로 남는다.

`novelty` 를 빼고 `1 - 친숙도` 만 남기면 관심사와의 상관은 -0.196 으로 떨어진다.
직교성 문제는 전적으로 `novelty` 항에 있었다.

### 그런데 남은 축도 죽어 있었다

`novelty` 를 제거하자 탐험 축의 실체가 드러났다.

```
explore = 1.0 인 글      112건 중 103건
서로 다른 값의 개수       4개
표준편차                 0.1136
```

거의 모든 글에 같은 값(0.15)을 더한다. **상수를 더하는 것은 순위를 바꾸지 않는다.**
예산의 15% 를 쓰면서 정렬에는 기여하지 않았고, 근거 계산에서는 112건 중 96건의
최대 기여 축이 되어 칩을 무의미하게 만들었다.

탐험은 점수 축으로는 성립하지 않는다 — 값이 고르면 순위를 안 바꾸고, 값이 갈리면
관련도와 정면으로 싸운다. **축에서 제거하고 가중치는 나머지 넷에 비례 배분했다.**
제대로 된 탐험은 §4.5 의 슬롯 쿼터로 해야 하며, 얼마나 섞을지는 제품 결정이라
정하지 않았다.

## 3. 원칙

> **모든 축을 `[0,1]` 로 정규화한 뒤에 가중치를 곱한다.**

이렇게 하면 가중치가 그 축이 가져갈 수 있는 **상한 지분**이 된다. 총점도 `[0,1]` 에 들어온다
(가중치 합 = 1.0). "품질 25%" 가 말 그대로 25% 가 된다.

정규화 방식을 고를 때 지킨 제약 세 가지.

- **결정적이어야 한다.** 점수가 Redis Sorted Set 에 저장되므로 후보 풀 구성에 따라
  값이 달라지면 캐시가 요청마다 의미가 달라진다. → 풀 상대(min-max·백분위) 대신
  **고정 기준값** 을 쓴다.
- **상한이 없는 축은 포화 곡선으로 누른다.** 조회수·좋아요는 상한이 없고 꼬리가 길다.
  잘라내면(clamp) 상위권이 뭉개지고, 선형으로 나누면 이상치 하나가 전체를 지배한다.
  로그가 둘 다 피한다.
- **0은 0으로 남아야 한다.** `log1p` 를 쓰는 이유다. 신호가 없는 글에 바닥 점수를
  깔아주면 축이 상수가 되어 순위 정보를 잃는다.

## 4. 축별 변환

공통 헬퍼 하나를 쓴다.

```java
/** 상한 없는 원점수를 [0,1] 로 누른다. ref 근처에서 1 에 수렴하고, 0 은 0 으로 남는다. */
private static double saturate(double raw, double ref) {
    if (raw <= 0) return 0.0;
    return Math.min(1.0, Math.log1p(raw) / Math.log1p(ref));
}
```

### 4.1 관심사

```java
double nInterest = saturate(interestMatchScore, INTEREST_REF);   // REF = 10
```

태그 점수 합은 상한이 없다(태그 수 × 태그당 점수). 실측 최대 12.

### 4.2 관계

구성 요소의 성격이 다르다. 팔로우·가입은 사용자가 **명시적으로 선언한** 관계이고,
친밀도 점수는 행동에서 **추정한** 값이다. 명시 신호에 바닥을 주고 친밀도로 올린다.

```java
double explicit = (followed ? 0.5 : 0.0) + (joined ? 0.4 : 0.0);
double affinity = saturate(authorInterest + commInterest * 1.2, RELATION_REF);  // REF = 20
double nRelation = Math.min(1.0, explicit + affinity * 0.5);
```

팔로우와 가입이 둘 다면 0.9 에서 시작한다. 현재의 15/20 비율(0.75:1)은
0.5/0.4 로 뒤집었다 — 팔로우는 사람을 고른 것이라 커뮤니티 가입보다 강한 의사표시다.
이 비율은 취향 문제이니 뒤집고 싶으면 두 상수만 바꾸면 된다.

### 4.3 품질 — 누적 총량이 아니라 시간당 반응률

가장 큰 변경이다. 총량을 경과 시간으로 나눈다.

```java
double rawQ  = like * 2.0 + cmt * 4.0 + view * 0.2;
double rate  = rawQ / (ageHours + QUALITY_PRIOR_HOURS);   // PRIOR = 4
double nQual = saturate(rate, QUALITY_RATE_REF);          // REF = 20
```

`QUALITY_PRIOR_HOURS` 가 분모의 바닥을 잡아 준다. 없으면 갓 올라온 글의
좋아요 1개가 `1/0 = ∞` 가 되어 신규 글이 영구히 1등을 한다.

효과: 4,000시간 동안 3,000점을 모은 글은 rate 0.75, 2시간 만에 50점을 모은 글은
rate 8.3. **"지금 반응이 오고 있는가" 를 재게 된다.** 누적 총량이 아니라.

신선도 축은 그대로 남긴다 — 반응이 아직 없는 새 글을 노출시키는 건 별개의 일이고,
근거 칩의 설명 가능성도 유지된다.

### 4.4 신선도 — 반감기

```java
double nFresh = Math.pow(0.5, ageHours / FRESH_HALFLIFE_HOURS);   // HALFLIFE = 24
```

`100/√(t+2)` 는 이미 감쇠 곡선이지만 눈금이 읽히지 않는다. 반감기로 쓰면
"하루 지나면 절반" 이라고 말할 수 있고, 커뮤니티 성격에 맞춰 조정할 근거가 생긴다.
토론형이면 72시간, 속보형이면 6시간.

### 4.5 탐험 — 점수 축에서 제거

§2 의 이유로 축 자체를 없앴다. 가중치 0.15 는 나머지 넷에 **비례 배분**했다.
축 하나를 뺀 것이지 균형을 다시 잡은 게 아니므로, 서로의 비율은 그대로 두었다.

| 축 | 이전 | 현재 |
|---|---|---|
| 관심사 | 0.15 | 0.18 |
| 관계 | 0.25 | 0.29 |
| 품질 | 0.25 | 0.29 |
| 신선도 | 0.20 | 0.24 |
| 탐험 | 0.15 | — |

탐험 자체는 **슬롯 쿼터** 로 되살렸다 — 아래.

### 4.5b 탐험 슬롯 쿼터

> **10건마다 1건** 은 한 번도 엮인 적 없는 작성자·커뮤니티의 글에 배정한다.
> 50건짜리 한 페이지에 5건이다. `knowra.feed.ranking.explore-slot-every=10`

개수가 아니라 **간격** 으로 정한 이유는 배치다. "50건 중 5건" 으로 세면 5건이 46~50번에
몰려도 규칙을 만족하는데, 거기까지 내려가는 사람이 없어 없는 것과 같다. 간격으로 두면
10·20·30·40·50번에 흩어지고 페이지 크기가 바뀌어도 규칙이 산다.

**5건을 고른 근거.** 49명 전원의 상위 50건을 실제로 정렬해 익숙한 글이 몇 건인지 셌다.

| 상위 50건 중 익숙한 글 | |
|---|---|
| 중앙값 | 13건 |
| 평균 | 15.7건 |
| 최대 | 46건 |
| 40건 이상인 사용자 | 3명 |
| 50건 전부인 사용자 | 0명 |

중앙값 사용자는 이미 37건이 낯선 글이라 쿼터가 **걸리지 않는다.** 오늘 치르는 비용이
사실상 0이라는 뜻이다. 실제로 걸리는 건 49명 중 3명뿐인데, 그중 최대치인 사용자는
50건 중 46건이 아는 사람이라 새로운 걸 만날 통로가 4칸밖에 없다. 팔로우를 더 할수록
더 닫힌다. **쿼터는 지금이 아니라 그 닫힘을 막는 하한선이다.**

3건이면 현재 아무에게도 안 걸려 넣으나 마나고, 8건 이상이면 10건 중 2건 가까이가
모르는 사람이라 피드가 성기게 느껴진다.

**적용 범위는 PERSONALIZED 뿐이다.** 인기·최신은 "지금 뜨는 것/새로 올라온 것" 을 보러
오는 화면이고, 팔로잉은 정의상 전부 아는 사람이라 낯선 글을 끼워 넣으면 그 피드가
약속한 것을 어긴다.

**동작 방식.** 정렬이 끝난 뒤, 낯선 글이 하나도 없는 블록에만 블록 밖에서 가장 점수가
높은 낯선 글을 끌어와 블록의 마지막 자리에 넣는다. 무작위가 아니라 이미 매긴 순위를
따르므로 품질이 떨어지지 않고, 나머지 글의 상대 순서는 그대로다.

**두 가지 구현 제약이 있었다.**

- 쿼터는 캐시 미스 재구축 시점에 적용해야 한다. 페이지 단위로 하면 캐시 히트·
  페이지네이션과 어긋난다.
- ZSET 의 score 에 원점수를 그대로 넣으면 Redis 가 되읽을 때 **쿼터 이전 순서로
  돌아간다.** 그래서 score 는 최종 순위를 인코딩한다 (§6.2).
- 어떤 글이 쿼터로 올라왔는지는 정렬 결과만으로 알 수 없어 별도 키
  (`feed:personalized:<sn>:explore`)에 남긴다. 캐시 히트에서도 같은 근거가 나와야 한다.

### 4.6 합산

```java
double total = W1 * nInterest
             + W3 * nRelation
             + W4 * nQual
             + W5 * nFresh;     // total ∈ [0, 1]
```

가중치 합이 1.0 이어야 이 성질이 성립한다. 깨져도 겉으로는 멀쩡히 동작하므로
(순위도 나오고 오류도 안 난다) **기동 시점에 검증한다** — `FeedRankingProperties#validate`.

## 5. 효과

### 착수 전 예측 (5축 기준)

같은 계정·같은 후보군에 제안 공식을 적용해 계산했던 값이다. 탐험 축을 없애기 전이라
다섯 축이다.

| 축 | 명목 가중치 | 현재 순위 기여도 | 제안 후 |
|---|---|---|---|
| 관심사 | 15% | 0.2% | 26.3% |
| 관계 | 25% | 1.4% | 37.9% |
| 품질 | 25% | 97.8% | 6.1% |
| 신선도 | 20% | 0.0% | 0.0% |
| 탐험 | 15% | 0.6% | 29.7% |

```
순수 인기순과의 스피어만 상관   0.9992 → 0.2678
평균 순위 이동                 0.77칸 → 33칸
```

개인화가 실제로 작동하기 시작한다. 탐험 29.7% 가 이때 이미 이상 신호였는데,
그 정체는 4단계에서야 드러났다 (§2).

### 적용 후 실측 (2026-09-23)

예측이 아니라 API 응답을 직접 잰 값이다. 같은 계정의 `/api/feed/personalized` 112건.

| 지표 | 1~2단계 예측 | 1~2단계 실측 | 3~6단계 실측 |
|---|---|---|---|
| 평균 순위 이동 | 33.0칸 | 32.9칸 | 30.8칸 |
| 최대 순위 이동 | 97칸 | 97칸 | 80칸 |
| 순위 동일 | 1건 | 1건 | 0건 |

근거(`feedReason`) 분포가 단계마다 어떻게 움직였는지가 더 많은 것을 말해 준다.

```
정규화 전        POPULAR 50                                      ← 축이 하나였다
1~2단계 후       FOLLOWING 46 · EXPLORE 39 · JOINED_COMM 15 · INTEREST 12
4단계 후         EXPLORE 96 · FOLLOWING 10 · JOINED_COMM 4 · INTEREST 2   ← 죽은 축이 드러났다
6단계 후         FOLLOWING 42 · POPULAR 39 · INTEREST 21 · JOINED_COMM 10
최종(1페이지)    FOLLOWING 28 · INTEREST 9 · JOINED_COMM 8 · EXPLORE 5
```

마지막 줄의 EXPLORE 5건이 쿼터다. 10·20·30·40·50번에 정확히 한 건씩 들어갔다.
이제 EXPLORE 는 "의도적으로 섞은 글" 이라는 진짜 근거다 — 4단계 후의 96건처럼
"딱히 이유 없음" 을 뜻하지 않는다.

가운데 줄이 §2 의 발견이다. `novelty` 를 빼자 탐험이 근거의 86% 를 독점했다 —
거의 모든 글에서 같은 값이었기 때문이다. 축을 제거하고 나서야 분포가 의미를 갖는다.

모드별 확인도 통과했다.

- 캐시 히트 재조회 시 순서와 근거가 완전히 동일하다.
- 2페이지에 1페이지와 겹치는 글이 없다.
- 인기·최신·팔로잉에는 EXPLORE 가 한 건도 섞이지 않는다.
- Redis 키 모두 TTL 부착 — 개인화·팔로잉 1800초, 인기·최신 300초,
  탐험 슬롯 목록 1800초.

**다만 제안 후 수치도 명목 가중치와 어긋난다.****다만 제안 후 수치도 명목 가중치와 어긋난다. 이건 시드 데이터의 한계다.**

- **신선도 0%** — 시드의 모든 글이 162~175일 된 것이라 반감기 24시간 기준으로
  전부 0 이다. 축이 고장난 게 아니라 이 데이터로는 측정이 불가능하다.
- **품질 6.1%** — 나이가 전부 비슷해 반응률이 좁은 구간에 몰린다.
  나이가 섞인 실데이터에서는 훨씬 커진다.
- **탐험 29.7%** — §4.5 에서 지적한 그 문제다. 쿼터로 옮기면 사라진다.

**명목 가중치는 상한일 뿐 실현 지분이 아니다.** 실현 지분은 데이터 분포에 달렸고,
그래서 아래 §8 의 계측을 상시로 붙여 두어야 한다.

## 6. 함께 고쳐야 하는 것 — 빠뜨리면 조용히 망가진다

### 6.1 모드 보정식 — 해결됨 (2단계)

```java
case "FOLLOWING" -> totalScore * 0.7 + (isFollowedAuthor ? 15.0 : 0.0) + (isJoinedComm ? 20.0 : 0.0);
case "POPULAR"   -> totalScore * 0.6 + qualityScore   * 0.4;
case "LATEST"    -> totalScore * 0.7 + freshnessScore * 0.3;
```

`totalScore` 가 `[0,1]` 이 되는 순간 이 식들은 전부 깨진다. 뒤에 붙은 항이 원점수
(15, 20, 수백, 수십)라서 보정항 하나가 총점을 1000배로 눌러버린다.

```java
case "FOLLOWING" -> total * 0.7 + ((followed ? 0.6 : 0.0) + (joined ? 0.4 : 0.0)) * 0.3;
case "POPULAR"   -> total * 0.6 + nQual  * 0.4;
case "LATEST"    -> total * 0.7 + nFresh * 0.3;
```

**이 변경은 선택이 아니라 필수다.** 적용 후 Redis 네 키의 점수가 모두 `[0,1]`
안에 있는 것으로 확인했다 (§5).

### 6.2 Redis 캐시 — 해결됨 (3단계)

문제는 같은 키에 세 곳이 서로 다른 의미로 썼다는 것이었다.

```java
feedCacheService.add(popularKey(), member, 0.0);                    // 글 생성: 0
feedCacheService.incrementScore(popularKey(), member, 2.0 or 4.0);  // 반응: 원점수 누적
feedCacheService.populate(popularKey(), computeScore(...));         // 재구축: 랭킹 점수
```

정규화 후 랭킹 점수가 `[0,1]` 로 내려가면서 반응 한 건(+2.0)이 최상위 글(0.338)의
6배가 되는 상태였다. `latest` 도 같은 구조였다 — 생성 시 epoch 초(약 1.7e9)를 넣었다.

**증분 갱신은 되돌릴 수 없다는 것이 결정의 근거다.** 품질이
`saturate(반응량 / (경과시간 + 4))` 라서 반응 한 건이 총점에 주는 영향이 글의 나이와
현재 점수에 따라 달라진다. 상수 델타로 표현할 수 있는 값이 아니다.
원점수 카운터로 되돌리는 선택지는 1단계가 고친 "누적 총량" 문제로 되돌아간다.

그래서 **ZSET 의 score 는 쓰는 곳이 한 군데, 의미도 하나** 가 되도록 통일했다.
정확히는 **최종 순위를 인코딩한 값** 이다 — 탐험 쿼터(§4.5b)가 정렬 뒤에 순서를
바꾸므로, 원점수를 그대로 넣으면 Redis 가 되읽을 때 쿼터 이전 순서로 돌아간다.
읽는 쪽(`reverseRange`)은 순서만 쓰므로 점수의 크기 자체는 의미가 없다.

- `add` 와 `incrementScore` 를 제거했다. 다른 척도를 넣던 유일한 통로였다.
- 새 글은 전역 피드를 **무효화** 한다. 다음 조회가 전체를 다시 계산하며 제자리에 넣는다.
- 반응은 캐시를 건드리지 않는다. 빈도가 높아 매번 재구축하면 비싸다.
  전역 피드 TTL 5분이 그 역할을 한다.
- `PostReactedEvent` 는 발행되지만 구독자가 없다. 의도적이며 그 이유를
  `FeedEventListener` 클래스 주석에 적어 두었다.

### 6.3 근거 칩 계산 — 해결됨 (5단계)

축이 비교 가능해졌으므로 **최대 기여 축을 그대로 고르는 방식** 으로 되돌렸다.
우선순위 우회 로직과 그 이유를 적은 주석을 함께 제거했다.

관계 축이 1위일 때는 세 경우로 갈린다 — 팔로우, 커뮤니티 가입, 그리고 둘 다 아닌데
행동으로 친밀도가 쌓인 경우. 마지막을 위해 `AFFINITY` 근거를 추가했다.
(칩 자체는 화면에서 내려가 있지만 `feedReason` 은 API 응답에 남아 있다.)

## 7. 상수 — 설정으로 뺐다 (6단계)

코드에 박지 않는 이유는 단순하다. **랭킹 상수는 반드시 여러 번 고치게 된다.**
`FeedRankingProperties` 가 `knowra.feed.ranking.*` 로 바인딩한다.

```properties
knowra.feed.ranking.weight-interest=0.18
knowra.feed.ranking.weight-relation=0.29
knowra.feed.ranking.weight-quality=0.29
knowra.feed.ranking.weight-freshness=0.24
knowra.feed.ranking.interest-ref=10.0
knowra.feed.ranking.relation-ref=20.0
knowra.feed.ranking.quality-rate-ref=20.0
knowra.feed.ranking.quality-prior-hours=4.0
knowra.feed.ranking.fresh-half-life-hours=24.0
```

기동 시 **가중치 합이 1.0 인지 검증하고, 아니면 기동을 막는다.** 설정으로 뺀 이상
누군가 한 축만 올리고 끝내는 일은 반드시 생기는데, 그래도 겉으로는 멀쩡히 동작하기
때문이다 — 순위도 나오고 오류도 안 난다.

**기본값은 시작점이지 결론이 아니다.** 시드 데이터는 파이썬으로 생성한 합성 데이터라
(`src/docs/seed_data.py`) 반응 수가 균일 분포이고 나이가 전부 6개월이다.

기준값은 원칙적으로 **해당 원점수의 p95** 여야 한다. 실사용 데이터가 쌓이면 다시 뽑는다.

```sql
-- quality-rate-ref 재보정
SELECT percentile_cont(0.95) WITHIN GROUP (
  ORDER BY (like_cnt*2.0 + cmt_cnt*4.0 + view_cnt*0.2)
           / (EXTRACT(EPOCH FROM (now()-frst_crt_dt))/3600 + 4))
FROM knowra_post.tbl_post;
```

## 8. 검증

정규화는 "돌아간다/안 돈다" 가 아니라 "분포가 의도대로인가" 의 문제다. 축이 자기
가중치보다 큰 지분을 먹기 시작해도 기능은 멀쩡히 동작한다. 그래서 재는 것은 결과값이
아니라 **척도** 다.

`FeedRankingTest` 20건이 이걸 지킨다.

- **상한 불변식** — 무작위 3,000건(조회수 폭주, 6년 된 글, 방금 올린 글 포함)에서
  모든 축이 `[0,1]`, 각 축의 기여가 자기 가중치 이하, 총점이 `[0,1]`.
- **모드 보정 척도** — 네 모드 모두 보정 후에도 `[0,1]`. 보정항에 원점수가 하나라도
  남으면 여기서 걸린다 (§6.1).
- **가중치 합** — 합이 1.0 이 아닌 설정은 예외로 막힌다.
- **품질의 의미** — 6개월간 12,000점을 모은 글보다 2시간 만에 200점을 모은 글이 높다.
  갓 올라온 글의 반응 1건이 1.0 이 되지 않는다.
- **`saturate` 성질** — 0은 0, 단조 증가, 기준값에서 1, 그 위로는 clamp.
- **콜드 스타트** — 신호가 전혀 없는 사용자도 품질·신선도로 순서가 갈린다.
- **탐험 쿼터** — 익숙한 글로만 찬 블록에는 끌어올리고, 이미 낯선 글이 있는 블록은
  건드리지 않는다. 끌어올리는 것은 낯선 글 중 점수가 가장 높은 것이고, 나머지 글의
  상대 순서는 보존된다. 배열 시프트가 틀리기 쉬운 자리라 특히 고정해 두었다.

여기에 더해 **기여도 계측** 을 상시로 붙이면 좋다. §5 의 축별 가중 표준편차를 뽑는
관리자 쿼리다. 어떤 축이 다시 독주하면 이 수치가 먼저 움직인다.

실데이터가 없는 동안 **A/B 로 좋아졌는지 판정할 수는 없다.** 지금 근거로 말할 수 있는
것은 "척도가 틀려서 세 축이 죽어 있었고, 네 번째는 축 자체가 성립하지 않았다" 까지다.
어떤 가중치가 옳은지는 실사용 지표가 필요하다.
