# 피드 랭킹 — 가중치 정규화 방안

대상: `com.knowra.post.service.FeedService#computeScore`
작성 근거: 2026-09-23 로컬 PostgreSQL 시드(게시글 112건, 사용자 49명) 실측

---

## 1. 진단 — 가중치가 비중이 아니다

현재 총점은 다섯 축의 가중합이다.

```java
totalScore = interestMatchScore * 0.15   // 관심사
           + relationScore      * 0.25   // 관계
           + qualityScore       * 0.25   // 품질
           + freshnessScore     * 0.20   // 신선도
           + exploreScore       * 0.15;  // 탐험
```

가중치가 "비중"이 되려면 곱해지는 값들이 **같은 자로 재어져야** 한다. 지금은 아니다.
각 축의 원점수는 정의상 범위가 전혀 다르다.

| 축 | 원점수 정의 | 실측 범위 |
|---|---|---|
| 관심사 | 태그 점수의 합 | 0 ~ 12 |
| 관계 | 15/20 플래그 + 친밀도 | 0 ~ 50 |
| 품질 | `like×2 + cmt×4 + view×0.2` (누적 총량) | 0 ~ 3,598 |
| 신선도 | `100 / √(경과시간+2)` | 1.6 ~ 57.7 |
| 탐험 | `(1-친숙도) × 신규성 × 20` | 0 ~ 20 |

품질만 세 자릿수다. 가중치를 곱한 뒤 실제로 순위를 흔드는 양(표준편차)을 재면 이렇게 된다.

| 축 | 명목 가중치 | **실제 순위 기여도** |
|---|---|---|
| 관심사 | 15% | 0.2% |
| 관계 | 25% | 1.4% |
| 품질 | 25% | **97.8%** |
| 신선도 | 20% | 0.0% |
| 탐험 | 15% | 0.6% |

가장 신호가 풍부한 계정(태그 7개, 팔로잉 13명, 커뮤니티 6개)으로 개인화 순서와
순수 인기순을 비교한 결과다.

```
스피어만 상관       0.9992
순위가 완전히 같음   112건 중 59건
평균 순위 이동      0.77 칸
최대 순위 이동      4 칸
```

**개인화 피드는 인기순이다.** 축이 다섯 개인 게 아니라 하나다.

원인은 두 가지가 겹쳐 있다.

- **척도 불일치** — 위 표 그대로다.
- **품질이 누적 총량** — 6개월 된 글도 그동안 쌓은 조회수를 영구히 유지한다.
  신선도는 더해지는 항이라 이 격차를 되돌리지 못한다.

## 2. 정규화만으로는 안 되는 두 번째 결함

**관심사와 탐험이 같은 신호를 부호만 바꿔 쓰고 있다.**

```java
double novelty = tagSns.stream()
        .mapToDouble(t -> userTagScores.getOrDefault(t, 0.0) == 0.0 ? 1.0 : 0.0)
        .average().orElse(0.0);
```

`novelty` 는 "내 태그와 안 맞을수록 1" 이고, `interestMatchScore` 는 "맞을수록 크다" 이다.
정의상 서로의 뒤집힌 값이다. 실측 상관은 **-0.9226**.

즉 W1(0.15)으로 밀어올린 글을 W6(0.15)이 거의 같은 크기로 도로 끌어내린다.
태그 기반 개인화의 순효과는 **0에 수렴한다.** 척도를 맞춰도 이 상쇄는 그대로 남는다.

`novelty` 를 빼고 `1 - 친숙도` 만 남기면 관심사와의 상관은 -0.196 으로 떨어진다.
직교성 문제는 전적으로 `novelty` 항에 있다.

## 3. 원칙

> **모든 축을 `[0,1]` 로 정규화한 뒤에 가중치를 곱한다.**

이렇게 하면 가중치가 그 축이 가져갈 수 있는 **상한 지분**이 된다. 총점도 `[0,1]` 에 들어온다
(가중치 합 = 1.0). "품질 25%" 가 말 그대로 25% 가 된다.

정규화 방식을 고를 때 지킨 제약 세 가지.

- **결정적이어야 한다.** 점수가 Redis Sorted Set 에 저장되므로 후보 풀 구성에 따라
  값이 달라지면 캐시가 요청마다 의미가 달라진다. → 풀 상대(min-max·백분위) 대신
  **고정 기준값** 을 쓴다.
- **상한이 없는 축은 포화 곡선으로 누른다.** 조회수·좋아요는 상한이 없고 꼬리가 길다.
  잘라내면(clamp) 상위권이 뭉개지고, 선형으로 나누면 이상치 하나가 전체를 지배한다.
  로그가 둘 다 피한다.
- **0은 0으로 남아야 한다.** `log1p` 를 쓰는 이유다. 신호가 없는 글에 바닥 점수를
  깔아주면 축이 상수가 되어 순위 정보를 잃는다.

## 4. 축별 변환

공통 헬퍼 하나를 쓴다.

```java
/** 상한 없는 원점수를 [0,1] 로 누른다. ref 근처에서 1 에 수렴하고, 0 은 0 으로 남는다. */
private static double saturate(double raw, double ref) {
    if (raw <= 0) return 0.0;
    return Math.min(1.0, Math.log1p(raw) / Math.log1p(ref));
}
```

### 4.1 관심사

```java
double nInterest = saturate(interestMatchScore, INTEREST_REF);   // REF = 10
```

태그 점수 합은 상한이 없다(태그 수 × 태그당 점수). 실측 최대 12.

### 4.2 관계

구성 요소의 성격이 다르다. 팔로우·가입은 사용자가 **명시적으로 선언한** 관계이고,
친밀도 점수는 행동에서 **추정한** 값이다. 명시 신호에 바닥을 주고 친밀도로 올린다.

```java
double explicit = (followed ? 0.5 : 0.0) + (joined ? 0.4 : 0.0);
double affinity = saturate(authorInterest + commInterest * 1.2, RELATION_REF);  // REF = 20
double nRelation = Math.min(1.0, explicit + affinity * 0.5);
```

팔로우와 가입이 둘 다면 0.9 에서 시작한다. 현재의 15/20 비율(0.75:1)은
0.5/0.4 로 뒤집었다 — 팔로우는 사람을 고른 것이라 커뮤니티 가입보다 강한 의사표시다.
이 비율은 취향 문제이니 뒤집고 싶으면 두 상수만 바꾸면 된다.

### 4.3 품질 — 누적 총량이 아니라 시간당 반응률

가장 큰 변경이다. 총량을 경과 시간으로 나눈다.

```java
double rawQ  = like * 2.0 + cmt * 4.0 + view * 0.2;
double rate  = rawQ / (ageHours + QUALITY_PRIOR_HOURS);   // PRIOR = 4
double nQual = saturate(rate, QUALITY_RATE_REF);          // REF = 20
```

`QUALITY_PRIOR_HOURS` 가 분모의 바닥을 잡아 준다. 없으면 갓 올라온 글의
좋아요 1개가 `1/0 = ∞` 가 되어 신규 글이 영구히 1등을 한다.

효과: 4,000시간 동안 3,000점을 모은 글은 rate 0.75, 2시간 만에 50점을 모은 글은
rate 8.3. **"지금 반응이 오고 있는가" 를 재게 된다.** 누적 총량이 아니라.

신선도 축은 그대로 남긴다 — 반응이 아직 없는 새 글을 노출시키는 건 별개의 일이고,
근거 칩의 설명 가능성도 유지된다.

### 4.4 신선도 — 반감기

```java
double nFresh = Math.pow(0.5, ageHours / FRESH_HALFLIFE_HOURS);   // HALFLIFE = 24
```

`100/√(t+2)` 는 이미 감쇠 곡선이지만 눈금이 읽히지 않는다. 반감기로 쓰면
"하루 지나면 절반" 이라고 말할 수 있고, 커뮤니티 성격에 맞춰 조정할 근거가 생긴다.
토론형이면 72시간, 속보형이면 6시간.

### 4.5 탐험 — 상수 배수를 빼고, `novelty` 는 버린다

```java
// 1단계: 크기 상수만 제거한다. 두 항 모두 이미 [0,1] 이라 곱도 [0,1] 이다.
double nExplore = (1.0 - familiarity) * novelty;

// 4단계: novelty 를 버린다 (§2).
double nExplore = 1.0 - Math.min(1.0, (authorInterest + commInterest) / EXPLORE_REF);
```

`× 20` 은 다른 축과 크기를 맞추려던 흔적이므로 1단계에서 제거한다.
`novelty` 삭제는 §2 의 이유로 필요하지만 성격이 다른 변경이라 **4단계로 분리했다** —
1단계는 순위를 바꾸지 않는 척도 교정에만 집중하고, 신호를 없애는 결정은 따로 본다.

다만 남은 `1 - 친숙도` 도 시드에서 112건 중 103건이 정확히 1.0 이다. 거의 상수라
순위 정보를 거의 주지 못한다. **탐험은 점수 항으로는 원래 잘 작동하지 않는 축이다** —
값이 고르면 순위를 안 바꾸고, 값이 갈리면 관련도와 정면으로 싸운다.

> 권장: 2단계에서 탐험을 점수 축에서 빼고 **슬롯 쿼터**로 옮긴다.
> 50건 중 N건을 "한 번도 상호작용한 적 없는 작성자·커뮤니티" 에 고정 배정하는 방식이다.
> 탐험량을 직접 통제할 수 있고, 관련도 점수를 훼손하지 않는다.
> 1단계에서는 위 형태로 유지해 변경 범위를 좁힌다.

### 4.6 합산

```java
double total = W1 * nInterest
             + W3 * nRelation
             + W4 * nQual
             + W5 * nFresh
             + W6 * nExplore;   // total ∈ [0, 1]
```

### 적용 후 실측 (2026-09-23, 1~2단계 반영)

예측이 아니라 API 응답을 직접 잰 값이다. 같은 계정의 `/api/feed/personalized` 112건.

| 지표 | 예측 | 실측 |
|---|---|---|
| 평균 순위 이동 | 33.0칸 | **32.9칸** |
| 최대 순위 이동 | 97칸 | **97칸** |
| 순위 동일 | 1건 | **1건** |

근거(`feedReason`) 분포도 뒤집혔다. 정규화 전에는 50건 전부 `POPULAR` 이었다.

```
적용 전  POPULAR 50
적용 후  FOLLOWING 46 · EXPLORE 39 · JOINED_COMM 15 · INTEREST 12 · POPULAR 0
```

Redis 에 저장된 점수도 네 키 모두 `[0,1]` 안에 있다 — 모드 보정식(§6.1)이
제대로 재조정되었다는 뜻이다.

```
feed:personalized:1   0.114 ~ 0.437
feed:following:1      0.354 ~ 0.606
feed:popular          0.090 ~ 0.338
feed:latest           0.105 ~ 0.141
```

**다만 제안 후 수치도 명목 가중치와 어긋난다. 이건 시드 데이터의 한계다.**

- **신선도 0%** — 시드의 모든 글이 162~175일 된 것이라 반감기 24시간 기준으로
  전부 0 이다. 축이 고장난 게 아니라 이 데이터로는 측정이 불가능하다.
- **품질 6.1%** — 나이가 전부 비슷해 반응률이 좁은 구간에 몰린다.
  나이가 섞인 실데이터에서는 훨씬 커진다.
- **탐험 29.7%** — §4.5 에서 지적한 그 문제다. 쿼터로 옮기면 사라진다.

**명목 가중치는 상한일 뿐 실현 지분이 아니다.** 실현 지분은 데이터 분포에 달렸고,
그래서 아래 §8 의 계측을 상시로 붙여 두어야 한다.

## 6. 함께 고쳐야 하는 것 — 빠뜨리면 조용히 망가진다

### 6.1 모드 보정식

```java
case "FOLLOWING" -> totalScore * 0.7 + (isFollowedAuthor ? 15.0 : 0.0) + (isJoinedComm ? 20.0 : 0.0);
case "POPULAR"   -> totalScore * 0.6 + qualityScore   * 0.4;
case "LATEST"    -> totalScore * 0.7 + freshnessScore * 0.3;
```

`totalScore` 가 `[0,1]` 이 되는 순간 이 식들은 전부 깨진다. 뒤에 붙은 항이 원점수
(15, 20, 수백, 수십)라서 보정항 하나가 총점을 1000배로 눌러버린다.

```java
case "FOLLOWING" -> total * 0.7 + ((followed ? 0.6 : 0.0) + (joined ? 0.4 : 0.0)) * 0.3;
case "POPULAR"   -> total * 0.6 + nQual  * 0.4;
case "LATEST"    -> total * 0.7 + nFresh * 0.3;
```

**이 변경은 선택이 아니라 필수다.**

### 6.2 Redis 캐시

`FeedCacheService` 의 점수 경로를 확인했다.

- `PERSONALIZED` / `FOLLOWING` / `LATEST` — 캐시 미스 때 후보 전체를 한 번에
  다시 채운다(`populate`). 정규화해도 **안전하다.**
- `POPULAR` — 안전하지 않다. 이미 두 척도가 섞여 있다.

```java
// FeedEventListener
feedCacheService.add(popularKey(), member, 0.0);                       // 생성: 0 점
feedCacheService.incrementScore(popularKey(), member, 2.0 or 4.0);     // 반응: 원점수 누적
// FeedService (cache miss)
feedCacheService.populate(popularKey(), computeScore(...));            // 재구축: 수백 점
```

지금도 `popularKey` 의 점수는 "반응 누적 카운터"(0~수십)와 "computeScore 결과"(수백)
사이를 오간다. 정규화하면 `computeScore` 쪽이 `[0,1]` 로 내려가므로 **좋아요 한 번이
전체 순위를 뒤집는다.** 기존 버그가 드러나는 것이지 새로 생기는 게 아니다.

1~2단계 적용 후 실측으로 확정됐다. `feed:popular` 의 점수 범위는 **0.090 ~ 0.338** 인데
`incrementScore` 가 더하는 값은 좋아요 2.0, 댓글 4.0 이다. 반응 한 건이 최상위 글의
6배 점수를 만든다. **3단계를 미루는 동안 `POPULAR` 피드는 반응이 발생하는 순간부터
순서가 무너진다.**

→ `POPULAR` 은 증분 갱신을 버리고 TTL 재구축으로 통일하거나, ZSET 을 순수 반응
카운터로 정의하고 랭킹 점수와 분리한다. **정규화와 같은 커밋에서 정해야 한다.**

### 6.3 근거 칩 계산

`applyFeedReasons` 는 축 기여도를 다시 계산한다. §1 때문에 지금은 우선순위 방식으로
피해 가고 있다.

```java
// 축별 크기를 그대로 비교하면 안 된다. 품질은 (...) 수백 단위인데 나머지는 한 자릿수라,
// 최대값을 고르면 거의 항상 "인기"가 된다.
```

정규화 후에는 축이 비교 가능해지므로 **최대 기여 축을 그대로 고르는 원래 방식으로
되돌릴 수 있다.** 우회 로직과 이 주석을 같이 제거한다. (칩 자체는 현재 화면에서
내려가 있지만 `feedReason` 은 API 응답에 남아 있다.)

## 7. 상수

```java
private static final double INTEREST_REF        = 10.0;
private static final double RELATION_REF        = 20.0;
private static final double QUALITY_RATE_REF    = 20.0;
private static final double QUALITY_PRIOR_HOURS =  4.0;
private static final double FRESH_HALFLIFE_HOURS = 24.0;
private static final double EXPLORE_REF         = 20.0;
```

**이 값들은 시작점이지 결론이 아니다.** 시드 데이터는 파이썬으로 생성한 합성 데이터라
(`src/docs/seed_data.py`) 반응 수가 균일 분포이고 나이가 전부 6개월이다.
실제 트래픽의 분포와 다르다.

기준값은 원칙적으로 **해당 원점수의 p95** 여야 한다. 실사용 데이터가 쌓이면 다시 뽑는다.

```sql
-- QUALITY_RATE_REF 재보정
SELECT percentile_cont(0.95) WITHIN GROUP (
  ORDER BY (like_cnt*2.0 + cmt_cnt*4.0 + view_cnt*0.2)
           / (EXTRACT(EPOCH FROM (now()-frst_crt_dt))/3600 + 4))
FROM knowra_post.tbl_post;
```

상수는 코드에 박지 말고 `@ConfigurationProperties` 로 빼서 재배포 없이 조정 가능하게
두는 편이 낫다. 랭킹 상수는 반드시 여러 번 고치게 된다.

## 8. 검증

정규화는 "돌아간다/안 돈다" 가 아니라 "분포가 의도대로인가" 의 문제라 단위 테스트만으로는
부족하다. 세 가지를 붙인다.

1. **상한 불변식** — 무작위 표본에서 각 축의 기여가 자기 가중치를 넘지 않고
   총점이 `[0,1]` 안에 있는지 단언한다. 정규화가 깨지면 여기서 먼저 걸린다.
2. **기여도 계측** — §5 표(축별 가중 표준편차)를 산출하는 관리자 쿼리 또는 로그를
   상설화한다. 어떤 축이 다시 독주하면 이 수치가 먼저 움직인다.
3. **골든 순서 테스트** — 고정 픽스처(글 N건 + 사용자 1명)로 상위 10건의 순서를
   스냅샷으로 잡는다. 상수를 건드릴 때 무엇이 바뀌는지 눈에 보인다.

실데이터가 없는 동안 **A/B 로 좋아졌는지 판정할 수는 없다.** 지금 근거로 말할 수 있는
것은 "척도가 틀려서 네 축이 죽어 있었다" 까지이고, 어떤 가중치가 옳은지는
실사용 지표가 필요하다.

## 9. 적용 순서

| 단계 | 내용 | 위험 | 상태 |
|---|---|---|---|
| 1 | `saturate` 헬퍼 + 다섯 축 정규화 (§4) | 낮음 | **완료** |
| 2 | 모드 보정식 재조정 (§6.1) | **필수 동반** | **완료** |
| 3 | `POPULAR` 캐시 척도 정리 (§6.2) | 중간, 설계 결정 필요 | 대기 |
| 4 | `novelty` 제거 (§2) | 낮음 | 대기 |
| 5 | 근거 칩을 최대 기여 축 방식으로 환원 (§6.3) | 낮음 | 대기 |
| 6 | 상수를 설정으로 외부화 (§7) | 낮음 | 대기 |
| 7 | 탐험을 슬롯 쿼터로 이전 (§4.5) | 별도 작업 | 대기 |

1~2 는 한 커밋이어야 한다. 3 은 선행 결정이 필요하므로 분리한다.

**3단계가 가장 급하다.** §6.2 의 실측대로, `POPULAR` 피드는 이제 반응 한 건에
순서가 무너지는 상태다. 시드에는 반응 이벤트가 없어 드러나지 않을 뿐이다.
